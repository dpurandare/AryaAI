# Sachivji vs. OpenClaw

A factual comparison based on this repository's own code (`src/main/agents/roles.ts`, `src/main/tools/`, `README.md`) and OpenClaw's public README, docs, and architecture pages (see Sources). Where a claim about OpenClaw depends on its docs rather than hands-on testing, it's phrased as "not a documented built-in" rather than an absolute "cannot" — see the note at the end on why that distinction matters here.

## Sachivji feature list

What ships today (`main`, released as 0.2.2) plus what's landed on the `design_change` branch heading to release 0.3.0 — both reflected below, since the redesign work is implementation-complete and only awaiting its manual test/release gate, not a future promise.

- **What it is**: a local-first, multi-agent AI desktop companion (Electron + TypeScript + Svelte) built around real business/office workflows — documents, databases, spreadsheets, APIs — not a general chatbot wrapper.
- **Multi-provider, including a genuinely free option**: Anthropic, OpenAI, Google (Gemini), Groq, and Mistral as hosted providers, plus Ollama for fully local/free models — selected the same way as any other provider, with live context-window detection read from the running Ollama server itself.
- **A multi-agent orchestrator with 11 named specialists** — Planner, Researcher, History Analyst, Developer, Data Access, Data Processor, Document Creator, Page Creator, Configurator, Email, and an MCP Operator — each with its own curated tool subset and tuned prompt. A request is automatically classified as simple or compound and, when compound, split into an ordered plan across the right specialists. A typed "handoff" passes each step's *real* output to the next as a file (diffed from the actual workspace, never a specialist's self-reported summary), so a later step works from real data instead of guessing.
- **Extensible without writing code or a plugin marketplace**: drop a Markdown file (frontmatter + a prompt) into a roles folder and it appears as a new specialist on your next message — validated, token-budget-checked, and still bound by the same per-tool confirmation and workspace rules as every built-in role.
- **Human-in-the-loop safety by default**: every mutating tool call shows an editable confirmation dialog before it runs, with session-level and per-tool auto-approve rules; a workspace-boundary guard enforced by real path canonicalization on every file tool.
- **A broad, curated tool set**: file read/write/list; Git + GitHub CLI; shell, Python (a managed virtual environment auto-created per workspace) and cloud CLIs (aws/az/gcloud); database connections (SQLite, Postgres, SQL Server, MySQL) with schema introspection, mechanical row tools, ad hoc SQL, and savable reusable queries; generic REST/OpenAPI integration (introspection, auth, auto-pagination, async job polling); structured-data tools for CSV/JSON/XML/HTML; web search plus semantic search over your own past conversations; native Word/PowerPoint/Excel generation with real formatting; email sending; and a Model Context Protocol (MCP) client for any MCP server, isolated to its own specialist so one connected server's tools can never leak into an unrelated request.
- **Visible process transparency**: live "which specialist is handling this" attribution, a real round-progress counter, a context/cost meter grounded in the model's actual context window, and a manual specialist picker to override routing when you know better than the router does.
- **Everything local**: sessions, messages, and settings in a local SQLite database — no cloud account or server-side storage. Export a session to Markdown, JSON, or PDF; import/export settings for team or enterprise provisioning (API keys and secrets excluded).
- **Status**: pre-1.0, under active, fast-moving development. The current focus (`design_change` → 0.3.0) is an architecture redesign that narrows role boundaries and defers loading of rarely-used capability so prompts stay small, cheap, and accurate as more tools/roles/MCP servers get added — a cost/latency/routing-quality investment, not a feature gap being filled.

## Enterprise readiness

**The claim, stated precisely**: Sachivji's architecture avoids several specific enterprise risks that OpenClaw's own documented default posture carries — but neither product is a finished, enterprise-certified package today, and the honest comparison is narrower than "Sachivji is enterprise-ready, OpenClaw is not."

**Where Sachivji's architecture is ahead, concretely:**
- **Data never leaves the device by design.** Sessions, messages, and settings live in a local SQLite file; the only outbound calls are the ones explicitly configured (a provider API, a connected MCP server, a web search). No analytics/telemetry, no server-side session storage.
- **Confirmation is the default, not an opt-in.** Every mutating tool call shows an editable dialog before it runs. OpenClaw's own docs state the opposite default — tools run directly on the host, with sandboxing "off by default" for personal use.
- **MCP containment limits blast radius.** A connected server's tools belong to one isolated specialist (MCP Operator) only — a data or coding task cannot reach a wiki's write tools by accident — and a server's own handshake `instructions` are never injected into any prompt, closing a documented MCP prompt-injection vector by construction.
- **Credentials are scoped, not ambient.** A specialist that doesn't need a database connection's password cannot see it — a tool call is the only path to a credential, never a shared context blob. (Observed directly, not assumed: asked to chart database data by a route that bypassed Data Access, the Developer specialist could not see the real database password and had to guess one — the guess failed, which is the boundary working as intended.)
- **Provisioning for a managed rollout.** Settings import/export lets an admin hand out a pre-configured provider/connection set without exposing secrets — API keys, MCP tokens, and DB passwords are excluded from the export by design.
- **No ambient external attack surface.** OpenClaw's own strength — 20+ messaging-channel integrations, an always-on daemon — is also a larger exposed surface: more channels and standing connections for a compromised credential or a malicious inbound message to reach. Sachivji only acts while the app is open and a user is actively driving it.

**Open gaps — not yet enterprise-complete, worth being direct about:**
- No RBAC, SSO, or multi-user model — a single-user, single-profile desktop app, not a managed fleet deployment. "Provisioning" today means handing someone a settings file, not centrally enforcing policy.
- No centralized audit log or SIEM integration. Tool calls are logged locally, not aggregated or exportable for a security team to monitor across a team's installs.
- Builds are not yet code-signed (macOS/Windows) — blocked on obtaining a paid Apple Developer ID and Windows Authenticode certificate. Until then, IT policies that block unsigned binaries are a real adoption blocker, not a hypothetical one.
- `shell_execute` is cwd-scoped to the workspace but explicitly **not** a sandbox — an approved script can still read/write outside the workspace folder. The confirmation dialog is the real control here, not a hard technical boundary.
- Auto-approve rules exist for convenience and can be configured broadly — nothing stops a user from weakening their own confirmation posture; there's no admin-enforced minimum today.
- No independent security audit or penetration test has been performed on either product, to this comparison's knowledge.

**Bottom line**: the architectural choices are real and defensible — local-first data, confirmation-by-default, MCP isolation, and credential scoping are genuine design decisions that reduce specific risks OpenClaw's documented defaults carry. But "can be guarded properly" is a claim about governance controls (RBAC, signed builds, centralized audit, SSO) that don't exist yet. The accurate pitch: **architected with fewer unforced security mistakes than a personal-use-first competitor, with a known, scoped list of governance features still to build** — not "enterprise-ready today."

## OpenClaw in Enterprise: The current scenario

**Short answer**: OpenClaw is being adopted in enterprises — but mostly through a third-party security layer bolted on top, not via its own native defaults, which carry a documented, real-world incident record, not just a hypothetical risk profile.

**Enterprises are showing up, via a hardening layer, not OpenClaw's own defaults.** NVIDIA announced "NemoClaw" at GTC 2026 — an enterprise security/governance stack wrapping OpenClaw: a kernel-level deny-by-default sandbox, an out-of-process policy engine a compromised agent can't override, and a privacy router that keeps sensitive data on local models. Its launch partners are named, large enterprises — Box, Cisco, Atlassian, Salesforce, SAP, and CrowdStrike ([The Batch, DeepLearning.AI](https://www.deeplearning.ai/the-batch/nvidias-enterprise-focused-nemoclaw-gives-openclaw-a-security-boost); [TheNextWeb](https://thenextweb.com/news/nvidia-nemoclaw-openclaw-enterprise-security)). That a major platform vendor built a whole separate enterprise-security product around OpenClaw is itself a signal: OpenClaw's own native defaults aren't considered enterprise-safe as shipped.

**Most real-world usage today is still ungoverned.** Palo Alto Networks' own security research characterizes typical current enterprise exposure as "shadow deployments" during a "viral experimentation phase" — individual employees or developers running it against corporate systems (Slack, Teams, Salesforce) without formal sanction — and states plainly it is "not yet production-ready" ([Palo Alto Networks](https://www.paloaltonetworks.com/blog/identity-security/how-autonomous-ai-agents-like-openclaw-are-reshaping-enterprise-identity-security/)).

**The risk record is specific, not hypothetical:**
- **CVE-2026-25253** — a one-click remote-code-execution flaw: a malicious link triggers a WebSocket handshake that leaks tokens and enables arbitrary shell command execution ([Palo Alto Networks](https://www.paloaltonetworks.com/blog/identity-security/how-autonomous-ai-agents-like-openclaw-are-reshaping-enterprise-identity-security/); [Sophos](https://www.sophos.com/en-us/blog/the-openclaw-experiment-is-a-warning-shot-for-enterprise-ai-security)).
- **30,000+ OpenClaw instances found exposed on the public internet**, with attackers probing newly-discovered ones within minutes — research from BitSight, reported independently by Sophos ([Sophos](https://www.sophos.com/en-us/blog/the-openclaw-experiment-is-a-warning-shot-for-enterprise-ai-security)).
- **A misconfigured Moltbook database exposed 1.5 million API authentication tokens and 35,000 email addresses** — disclosed by Wiz ([Palo Alto Networks](https://www.paloaltonetworks.com/blog/identity-security/how-autonomous-ai-agents-like-openclaw-are-reshaping-enterprise-identity-security/)).
- **Malicious "skills" published to ClawHub distributed roughly 400 malware packages within days** of going live ([Sophos](https://www.sophos.com/en-us/blog/the-openclaw-experiment-is-a-warning-shot-for-enterprise-ai-security)).

**Sophos' own stated verdict**: *"OpenClaw should be considered an interesting research project that can only be run 'safely' in a disposable sandbox with no access to sensitive data."*

**Bottom line**: OpenClaw's enterprise footprint is real and growing, but today it comes from two different places that shouldn't be conflated — (1) sanctioned adoption wrapped in a serious third-party hardening layer (NemoClaw/OpenShell), and (2) unsanctioned "shadow" usage by individual employees against corporate systems, running on the native defaults that carry the incident record above. Neither matches a mature, self-contained enterprise-ready product, and both are consistent with the Enterprise readiness assessment above.

*A note on sourcing*: figures reported elsewhere during this research — specific percentages of enterprise users, total active-user counts, or adoption-rate projections — turned up only on sites without a track record this comparison could verify, so they are deliberately left out. Everything stated above was corroborated against named security research outlets.

## What Sachivji does that OpenClaw does not (or not out of the box)

1. **A fixed roster of named specialist agents with automatic request decomposition, and a typed handoff between them.** Sachivji's orchestrator classifies a request as simple or compound and, for compound requests, builds an ordered plan across named specialists (Researcher, Developer, Data Access, Data Processor, Document Creator, Page Creator, History Analyst, Configurator, Email, MCP Operator — see the feature list above), each with its own curated tool subset and tuned system prompt. A later step receives the real output of an earlier one as a file, verified against the actual workspace, not a prose summary it has to take on faith. OpenClaw has a generic subagent primitive (`subagents`, `agents_list`, `agents_wait`) for spawning and coordinating agents, but no predefined "who's good at what" roster, no automatic compound-request decomposition, and no equivalent verified data handoff between agents.
2. **Native, richly-formatted Office document generation, built into the core app.** `.docx` with real Word headings, tables, bulleted/numbered lists, and inline bold/italic/code formatting; `.pptx` slide decks via a dedicated composition flow; `.xlsx` with bold/shaded headers, real cell borders, and auto-sized columns. OpenClaw's own tools documentation lists no built-in Word/PowerPoint/Excel generation — this would need a plugin.
3. **First-class configured database connections** (SQLite/Postgres/SQL Server/MySQL): schema introspection, mechanical row-level tools (list/count/find rows with no SQL needed), ad hoc SQL execution, and the ability to save a working query as its own reusable named tool for next time. Not a documented OpenClaw built-in.
4. **Generic REST/OpenAPI integration as a structured workflow**: introspect an OpenAPI/Swagger spec, call any endpoint with per-connection auth, auto-follow pagination, poll async jobs. OpenClaw's integrations are pre-built connectors to specific services, not a point-at-any-API system.
5. **Per-call, editable human-in-the-loop confirmation as the primary safety mechanism.** Every mutating tool call shows a dialog with the exact arguments (editable before approving), plus session-level and per-tool auto-approve rules. OpenClaw's default posture runs tools directly on the host with no per-call confirmation gate — safety comes from optional sandboxing and deterministic policy you configure yourself, which its own docs note is "off by default" for personal use.
6. **True local/free model support as an equal first-class option.** Ollama with no API key, selected the same way as any hosted provider, including live context-window detection read directly from the running Ollama server (correcting for Ollama's own default of loading a model at a much smaller runtime context than it's capable of). OpenClaw is model-agnostic too, but by embedding vendor agent harnesses (Claude Agent SDK, Codex, Copilot SDK) as plugins rather than talking to provider chat APIs directly.
7. **Workspace-boundary sandboxing enforced by real path canonicalization** (`WorkspaceGuard`) on every file tool, restricting all file operations to one configured folder regardless of what a tool is asked to touch.
8. **Visible process transparency**: live "which specialist is handling this" attribution in the transcript, a manual specialist-picker override, a real round-progress counter ("round 3/12"), and a context/cost meter grounded in the model's actual context window rather than a static guess.
9. **Local semantic search over your own past chat sessions** in this app, including the currently active one.

## What OpenClaw does that Sachivji does not

1. **Reaches you anywhere.** Native integrations with 20+ messaging channels (WhatsApp, Telegram, Discord, Slack, Microsoft Teams, Signal, iMessage, Google Chat, and more), plus native companion apps for macOS, iOS, Android, Windows, and Linux — including real mobile apps. Sachivji is an Electron desktop app only (macOS/Windows/Linux), with no mobile client and no messaging-platform presence.
2. **Runs as a persistent, always-on Gateway/daemon** that can act proactively/asynchronously (scheduled via built-in `cron`/heartbeat tools) even when you're not actively chatting — genuine ambient automation. Sachivji only acts while the app is open and you're actively sending messages.
3. **Device "nodes"**: camera, screen, voice, and other device-local capabilities as input/output surfaces on a phone or other connected device. Sachivji has no device-node concept.
4. **A public plugin ecosystem and marketplace (ClawHub)**: 100+ pre-built "AgentSkills" and 50+ third-party integrations (productivity tools, smart-home devices, music/audio platforms, automation tools) anyone can install or publish. Sachivji's extensibility is MCP server connections (a real, comparable protocol-level extension point, configured in Settings), but there's no public marketplace or community skill-sharing hub.
5. **Multi-user/team collaboration on one shared assistant deployment**: real-time presence, session ownership and participants, teammates observing, steering, or taking over a running session together. Sachivji is single-user/single-session, with no shared-deployment concept.
6. **Built-in generative media tools**: image, music, and video generation, plus text-to-speech. Sachivji has none of these.
7. **Embeds vendor coding-agent harnesses directly** (Claude Agent SDK, OpenAI's Codex harness, GitHub Copilot SDK) as plugins, inheriting each vendor's own native agentic-coding capabilities as they evolve. Sachivji implements its own orchestrator/tool-calling loop directly against each provider's plain chat-completions API.
8. **Much larger scale and backing**: an independent nonprofit foundation (501(c)(3)) with corporate sponsors, 390,000+ GitHub stars, and an active outside-contributor base — a far broader existing ecosystem of ready-made integrations than a single small app is likely to build alone.

## How to read this comparison

- OpenClaw's philosophy is "small core, large plugin ecosystem" — nearly every gap listed under it above (Excel writing, SQL access, etc.) could in principle be filled by installing or writing a plugin/skill. This comparison is about what ships **built-in and documented today**, not what's theoretically reachable through its plugin SDK.
- Sachivji's philosophy is close to the opposite: a fixed, curated, built-in tool set (no plugin marketplace beyond MCP), traded for tighter, more specific tool design (e.g., a mechanical `db_list_rows` instead of hand-written SQL) and an approval-first safety model for anything that mutates state. The one deliberate exception is user-defined roles (a Markdown file, no plugin SDK) — a modest, local, non-marketplace extension point, not an answer to ClawHub's scale.
- These are different products solving different problems: OpenClaw is a proactive, ambient, cross-device personal/life-automation assistant reachable through the channels you already use; Sachivji is a desktop, session-based, business/office-workflow assistant (documents, databases, APIs, spreadsheets) built around a curated multi-specialist orchestrator and an explicit human-approval safety model.
