  **Follow-up, same day — URL fabrication hardened from advisory to enforced, per explicit user request ("I don't want the model or the agent to speculate the URL... if you need to harden it, do it").** A prompt-only fix (never guess an article URL) was already tried once and didn't reliably hold — found live again in the user's own real session (`sqlite3`-queried, not just observed in the UI): the model fabricated a *variant* of a real article's URL (a real slug it had already seen, with an invented numeric ID) rather than a wholly invented one, a subtler case a prompt alone can't reliably catch.   **Follow-up, same day, a real bug found from an actual user session, not hypothetical**: `parse_html`'s reader-mode extraction discards every `<a href>` — fine for a single article, actively harmful for a listing/topic/search-results page, whose whole value *is* its links. Live-verified against the exact real page and headline from the original failure: the real link list now includes the exact article the user needed, with a genuine `articleshow` ID that resolves 200, not a fabricated one.

- [ ] 73. Office document tools: read/create `.docx`/`.pptx` files, read/modify/create `.xlsx` files (Coding or Data role — TBD). **Design settled 2026-09-17, revised 2026-09-17 evening — scope deliberately narrowed, not yet implemented:**
  - **`.xlsx`**: `exceljs` handles the full read/modify/create lifecycle natively (loads a real existing workbook, edits it, re-saves) — no gap here, unaffected by the scope change below.
  - **`.docx`/`.pptx`: modifying an existing file is explicitly OUT of scope — dropped, not deferred.** Neither `docx` nor `pptxgenjs` can load an existing file, so the only way to "modify" one was always an extract → modify → regenerate flow — a content *rebuild*, not a true in-place edit. User's own call after this was flagged honestly as lossy (a document with custom styles, exact table formatting, a branded template, or precise slide layout/theme would come back looking different, not identical): not worth the real implementation cost (a docx extractor, a hand-built pptx extractor, transform logic, rebuild logic) for a result that would routinely disappoint someone expecting their actual document edited in place.
  - **What stays in scope for `.docx`/`.pptx`**: reading an existing file's content (via `mammoth` for docx → HTML/text; a small custom pptx-text extractor via `jszip` + `fast-xml-parser`, pulling `<a:t>` runs per slide — no rebuild involved, so no fidelity risk) and creating a brand-new file from scratch via `docx`/`pptxgenjs`.
  - **When a user asks to edit an existing `.docx`/`.pptx`**: say plainly that in-place editing isn't supported for this format, and offer to create a new document instead — reading the original's content first (via the read path above) to work from, if that's useful context, rather than silently attempting a lossy rebuild and calling it an edit.

Deliberately different in kind, not a contradiction of that decision: this only works for a file *deliberately authored as a template* with known merge fields, not an arbitrary existing document someone wants tweaked.
    - **Storage**: a `templates/` subfolder inside the existing workspace root (confirmed with the user over a Settings-managed store) — no new storage mechanism, no new Settings UI; the user drops template files there and references them by name/path like any other workspace file.
    - **New tool** (name TBD, e.g. `office_fill_template`): template path + a data object (with array fields for any `{#loop}` sections) → substituted output written to a new file. Before filling, reuses the same text-extraction already planned for the read path above (mammoth/pptx-text-extractor) to scan the template for its `{...}` placeholders, so the agent knows what data it needs rather than guessing blind.

- [ ] 75. `.env` file as an alternative to OS-keychain secret storage — give the user a choice of where secrets (provider API keys, DB/API/MCP connection credentials) live, instead of only `safeStorage`-encrypted `credentials.enc.json` (`src/main/security/keychain.ts`). Flagging the real tradeoff up front since it cuts against this project's own stated security posture (`thouthts.md` #7: "API keys must be stored using the OS-native secure storage... never in a plaintext config file"): a `.env` file is plaintext on disk by nature, readable by any process/user with filesystem access, and a common accidental-commit/leak vector — very different guarantees from `safeStorage` (OS Keychain/DPAPI/libsecret). **Design settled 2026-09-17, not yet implemented:**

  - **Entry points**: offered as a choice on a new **first-run setup screen** (the first time Sachivji itself launches with nothing configured yet — not the OS installer/`.dmg`/`.exe`/`.deb`, which can't run custom app UI), and separately, later, as a one-time action in Settings for someone who started on Keychain.
  - **One-directional migration, not a toggle**: switching Keychain → file is a single one-time action — once done, everything currently in the keychain is exported to `.env`, and from that point on *all* reads/writes (new secrets included) go to `.env` only; the keychain is no longer consulted. There is no UI path back to Keychain.
  - **Settings UI**: shows the current mode as a **read-only indicator** ("Secret storage: OS Keychain" / "Secret storage: File (`~/.sachivji/.env`)"), with the one-time switch action visible only while still on Keychain.

- [ ] 76. Widen the Data tool's DB support beyond SQLite/Postgres — SQL Server, MySQL/MariaDB, Oracle as the first concrete targets; DynamoDB/Cosmos DB/MongoDB-style stores explicitly out of scope for this item (see below). **Analysis done 2026-09-17, not yet implemented:**
  - **The architecture already fits this well**: `src/main/tools/db/types.ts`'s `DbDriver` interface (`introspectSchema()`, `execute(sql, params)`, `close()`) plus `driver-factory.ts`'s connection-`engine`-keyed factory is a clean, small extension point — the existing `PostgresDriver` is ~75 lines end to end. Adding a new SQL-speaking engine is a bounded, precedented unit of work per engine, not a redesign.
  - **Real constraint, worth stating plainly**: "the connection/dialect info is on the internet, the agent can look it up" solves the *knowledge* problem, not the *dependency* problem. Each engine needs a real compiled Node driver library added to `package.json` and bundled at build time — an agent inside a packaged, signed Electron app can't fetch/install a new driver at runtime, and having it dynamically load arbitrary code based on a web search would be a real RCE-shaped risk, not a feature. This item is "we add support for a new engine ahead of time," not "the agent adds its own DB support on the fly."
  - **Per-engine, not equally easy**: SQL Server (`mssql`, pure JS, no native install) and MySQL/MariaDB (`mysql2`, pure JS) are the easy additions. Oracle (`oracledb`) is the official driver but requires the separate Oracle Instant Client native libraries on the machine — real extra install friction for the user, worth flagging up front rather than discovering at ship time.
  - **Concrete per-engine work**: a new driver class implementing `DbDriver`; widen `connections.ts`'s `engine` union (currently hardcoded `'sqlite' | 'postgres'`, also duplicated as `DbEngine` in `shared/ipc-contract.ts`) and `SettingsPanel.svelte`'s connection-type dropdown + per-engine field set; generalize `param-binding.ts`'s hardcoded 2-way `$N`/`?` ternary to a real per-engine placeholder style (SQL Server named `@name`, Oracle positional `:1`, MySQL `?` like SQLite); an engine-specific `introspectSchema()` catalog query (Oracle uses `ALL_TABLES`/`ALL_TAB_COLUMNS`, not `information_schema`, unlike Postgres/SQL Server/MySQL which all share that convention).
  - **Where the agent's own reasoning legitimately helps** (the part of the original idea that's actually right): once a driver+connection exist, the model generating SQL against it benefits from knowing the target dialect (Oracle's `ROWNUM`/`VARCHAR2`, SQL Server's `TOP`/`GETDATE()`) — mostly already in an LLM's training knowledge, reinforced via the Data role's system prompt (which connection this is, so which dialect to write) rather than needing a live web search on every query.
  - **Explicitly out of scope here**: DynamoDB and similarly-shaped NoSQL/cloud stores (Cosmos DB, MongoDB) aren't SQL at all — no `execute(sql)` concept applies, it's an item-level API (getItem/putItem/query by partition+sort key). Doesn't fit `DbDriver`; would need its own tool family closer in shape to `api_call` than to `db_execute_sql` — a separate, unsized design exercise, not a new driver plugged into this item's existing shape.
