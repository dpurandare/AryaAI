- [ ] 75. `.env` file as an alternative to OS-keychain secret storage — give the user a choice of where secrets (provider API keys, DB/API/MCP connection credentials) live, instead of only `safeStorage`-encrypted `credentials.enc.json` (`src/main/security/keychain.ts`). Flagging the real tradeoff up front since it cuts against this project's own stated security posture (`thouthts.md` #7: "API keys must be stored using the OS-native secure storage... never in a plaintext config file"): a `.env` file is plaintext on disk by nature, readable by any process/user with filesystem access, and a common accidental-commit/leak vector — very different guarantees from `safeStorage` (OS Keychain/DPAPI/libsecret). **Design settled 2026-09-17, not yet implemented:**
  - **Location**: a dedicated `~/.sachivji/.env` (home-folder directory, not the app's `userData` folder).
  - **Entry points**: offered as a choice on a new **first-run setup screen** (the first time Sachivji itself launches with nothing configured yet — not the OS installer/`.dmg`/`.exe`/`.deb`, which can't run custom app UI), and separately, later, as a one-time action in Settings for someone who started on Keychain.
  - **One-directional as a UI action, not one-directional as a data flow — revised 2026-09-19**: switching Keychain → file is still a single one-time user-facing action with no UI path back, but the keychain is NOT abandoned afterward. Everything currently in the keychain is exported to `.env` at switch time, `.env` becomes the primary source of truth for all reads, but **every write after switchover dual-writes to both `.env` and the keychain** (new secrets included) — the keychain stays a complete, current backup indefinitely, not a frozen snapshot. If `.env` can't be read at all (missing/corrupted), the app falls back to reading from the keychain if it still has the data; only if *both* are empty does the app treat it as a fresh, unconfigured start (recreate settings via Settings, same as a new install). No case of a corrupted-but-*readable* `.env` needs special handling beyond that same fallback, since `0600` permissions already rule out another local user being the cause.

- [ ] 76. Widen the Data tool's DB support beyond SQLite/Postgres — SQL Server, MySQL/MariaDB, Oracle as the first concrete targets; DynamoDB/Cosmos DB/MongoDB-style stores explicitly out of scope for this item (see below). **Analysis done 2026-09-17, not yet implemented:**
  - **The architecture already fits this well**: `src/main/tools/db/types.ts`'s `DbDriver` interface (`introspectSchema()`, `execute(sql, params)`, `close()`) plus `driver-factory.ts`'s connection-`engine`-keyed factory is a clean, small extension point — the existing `PostgresDriver` is ~75 lines end to end. Adding a new SQL-speaking engine is a bounded, precedented unit of work per engine, not a redesign.
  - **Real constraint, worth stating plainly**: "the connection/dialect info is on the internet, the agent can look it up" solves the *knowledge* problem, not the *dependency* problem. Each engine needs a real compiled Node driver library added to `package.json` and bundled at build time — an agent inside a packaged, signed Electron app can't fetch/install a new driver at runtime, and having it dynamically load arbitrary code based on a web search would be a real RCE-shaped risk, not a feature. This item is "we add support for a new engine ahead of time," not "the agent adds its own DB support on the fly."
  - **Per-engine, not equally easy**: SQL Server (`mssql`, pure JS, no native install) and MySQL/MariaDB (`mysql2`, pure JS) are the easy additions. Oracle (`oracledb`) is the official driver but requires the separate Oracle Instant Client native libraries on the machine — real extra install friction for the user, worth flagging up front rather than discovering at ship time.
  - **Concrete per-engine work**: a new driver class implementing `DbDriver`; widen `connections.ts`'s `engine` union (currently hardcoded `'sqlite' | 'postgres'`, also duplicated as `DbEngine` in `shared/ipc-contract.ts`) and `SettingsPanel.svelte`'s connection-type dropdown + per-engine field set; generalize `param-binding.ts`'s hardcoded 2-way `$N`/`?` ternary to a real per-engine placeholder style (SQL Server named `@name`, Oracle positional `:1`, MySQL `?` like SQLite); an engine-specific `introspectSchema()` catalog query (Oracle uses `ALL_TABLES`/`ALL_TAB_COLUMNS`, not `information_schema`, unlike Postgres/SQL Server/MySQL which all share that convention).
  - **Where the agent's own reasoning legitimately helps** (the part of the original idea that's actually right): once a driver+connection exist, the model generating SQL against it benefits from knowing the target dialect (Oracle's `ROWNUM`/`VARCHAR2`, SQL Server's `TOP`/`GETDATE()`) — mostly already in an LLM's training knowledge, reinforced via the Data role's system prompt (which connection this is, so which dialect to write) rather than needing a live web search on every query.
  - **Explicitly out of scope here**: DynamoDB and similarly-shaped NoSQL/cloud stores (Cosmos DB, MongoDB) aren't SQL at all — no `execute(sql)` concept applies, it's an item-level API (getItem/putItem/query by partition+sort key). Doesn't fit `DbDriver`; would need its own tool family closer in shape to `api_call` than to `db_execute_sql` — a separate, unsized design exercise, not a new driver plugged into this item's existing shape.
  - **Resolved 2026-09-19 — implementation order**: SQL Server (`mssql`) first, but designed to be added-to incrementally rather than all-at-once.
  - **New capability, added 2026-09-19 — allowlisted runtime install.** User's own framing: it should be possible to add support for a new DB type "when the app is running," not only via a future release. Real constraint confirmed unchanged from above: the app can't safely fetch/install *arbitrary* driver code at runtime (RCE-shaped risk). Resolved design: a small, code-curated allowlist of pure-JS driver packages *not yet bundled* — the allowlist itself is only ever extended by us via an app update (never user- or agent-editable), but once a package is on the allowlist, the running app can `npm install` just that package on demand, behind an explicit confirmation dialog, the first time a user actually needs it — no bundle-size cost paid for engines nobody uses, no waiting for the next release once something is allowlisted. Doesn't help for native-binary drivers (Oracle's `oracledb`) — those still require the app-bundled path. Exact install location (must be outside the read-only `app.asar`, likely a `userData` subfolder) and integrity verification before `require()`-ing an installed package are implementation-time details, not decided here.

- [ ] 77. Orchestrator capability: **isolated delegation** — a delegate call that gets a scoped, minimal context and its own independent round budget, instead of today's behavior. General mechanism, not tied to any one role; item #78 (presentation/page creation) is its first real consumer. **Design settled 2026-09-17 evening, not yet implemented:**
  - **The gap, confirmed in the current code, not assumed**: `dispatchDelegate` (`orchestrator.ts`) builds every nested call's conversation as `[...conversation, taskMessage]` — the *entire* parent conversation, unconditionally — and threads the *same* `RunState` object into every nested `runLoop`, so `state.roundsUsed` against `MAX_TOTAL_ROUNDS = 12` is one shared pool across the whole run, delegates included. Fine for today's roles (a handful of delegate calls per turn, each needing the parent's context to do its job), wrong for a role whose task is bounded and self-contained and gets invoked *repeatedly* in one turn (e.g. once per slide) — every call would drag in the full accumulated conversation, and N such calls would collectively exhaust the same 12-round ceiling the rest of the turn still needs.
  - **Per-role opt-in, not a blanket behavior change**: add an `isolated?: boolean` and `maxRounds?: number` to the `Agent` interface (`orchestrator.ts`)/role definition (`roles.ts`). Every existing role leaves both unset and keeps today's exact behavior (full inherited context, shared budget) — zero behavior change for planning/research/coding/terminal-devops/data/distribution.
  - **What `isolated: true` changes in `dispatchDelegate`**: the nested conversation becomes just `[{role: 'user', content: taskMessage}]` — the task/brief the calling role hands it, nothing else — and the nested `runLoop` gets a **fresh `RunState`** (its own `roundsUsed` starting at 0, capped at `agent.maxRounds ?? MAX_TOTAL_ROUNDS`) instead of the parent's shared one. Token usage from the isolated call's fresh `RunState` still rolls up into the parent's cumulative `inputTokens`/`outputTokens` afterward (and from there into `session_usage`) — cost accounting stays honest and complete; only the *round ceiling* is decoupled, not the money.
  - **Why this matters beyond presentations**: any future role with the same shape (bounded, self-contained, invoked repeatedly per turn on a narrow brief) can opt into this without another orchestrator change — this is the general primitive, not a one-off special case wired only for page creation.

- [ ] 78. Presentation/deck creation, built on #77's isolated delegation — `coding` plans a deck's structure/flow/template and delegates each planned slide to a new, isolated `page-creator` role that picks a fitting visual/infographic idea for that slide's content and builds it via `pptxgenjs`. **Design settled 2026-09-17 evening, not yet implemented:**
  - **Two-tier split, confirmed as the right call over a template-menu approach**: `pptxgenjs` genuinely supports infographic-grade output (170+ shape types, 9 chart types, images/SVGs, tables, precise positioning/layering — checked directly against the package's real type definitions, not assumed), so a fixed menu of pre-built layouts would under-use it. `coding` (already the natural owner of file-creation work per #73) decides *what* slides exist and in what order/template; the new `page-creator` role decides *how* one slide's content becomes a visual, with real creative latitude over shape/color/icon/chart choices — not a rigid template picker.
  - **`page-creator` is isolated** (#77): each `delegate_to_page_creator` call gets only that slide's brief (heading, key content/data points, tone/style notes — whatever `coding` decides to hand it), not the whole deck-planning conversation, and its own round budget (proposed cap: **6** — enough for a real think-then-build-then-refine cycle on one page, clearly bounded, fully decoupled from the parent's 12).
  - **Round economy via tool shape, not via limiting creativity**: rather than one tool call per shape (a rich infographic page could otherwise cost 5+ rounds on its own), `page-creator` gets a single tool, `pptx_compose_slide`, taking a *whole page's* visual spec in one call — an array of elements (shape/text/image/chart/table), each with its own type, position/size, and content/style. The model still freely designs the full layout; it just expresses that design as one structured call instead of many sequential ones, keeping even a busy page to roughly 2-3 rounds.
  - **Resolved 2026-09-19 — slide lifecycle**: `coding` owns `pres.addSlide()`/the file lifecycle. It creates the `Presentation` object, calls `addSlide()` for each planned slide, and hands `page-creator` that specific slide object to populate via `pptx_compose_slide` — `page-creator` never touches file save/lifecycle, purely fills content into a slide it's given. Chosen over letting `page-creator` own it per-call, since that would require the isolated delegate to hold write access to shared mutable state, cutting against #77's whole "minimal isolated context" point.
  - **Resolved 2026-09-19 — failed/ugly slide handling**: not a hard fallback-or-stop binary. When `page-creator` exhausts its 6-round budget without a usable result, `coding` first retries automatically once with its own corrective instruction (e.g. "simplify, fewer elements") — a bounded, no-user-interruption fix for the common case. If that automatic retry also fails, `coding` stops and asks the user directly for their own additional instruction for that slide (e.g. "make it a simple bar chart instead") before trying again, rather than silently substituting a plain-text fallback or guessing indefinitely.
  - **Still open, deliberately deferred to implementation time**: `pptx_compose_slide`'s exact input schema (how each element type's fields are shaped) — a technical detail better designed against `pptxgenjs`'s real API when the tool is actually built than decided in the abstract now.

- [ ] 79. Email-sending sub-agent — an isolated `email` role (per #77) that any specialist (or the Orchestrator) hands a loose brief to ("email the team about this") along with recipient address(es) and optional attachment file paths (workspace-relative, same convention as `read_file`/`write_file`); the role drafts the actual subject/body itself, sends it, and confirms back with the result. **Design continued 2026-09-19, credentials researched, not yet implemented:**
  - **Likely library**: `nodemailer` (MIT-0, the standard Node SMTP/email-sending library — confirmed real via `npm view`, not assumed). Supports file-path attachments directly, matching what's being asked for.
  - **Resolved 2026-09-19 — full reasoning role, not a plain tool**: unlike a fully-specified send, the actual ask is often "email X about Y" rather than caller-supplied subject/body — composing the message *is* the task, so this is a genuine `page-creator`-shaped candidate for #77's isolated delegation (bounded, own round budget), not a plain mutating tool like `write_file`.
  - **Gmail — resolved, real and durable today**: app passwords remain a fully working SMTP path for personal Gmail accounts with 2-Step Verification enabled (Google's stated direction is OAuth2 for new integrations, but app passwords are not deprecated) — matches `nodemailer`'s built-in `service: 'gmail'` transport preset directly. Sources: [Nodemailer: Using Gmail](https://nodemailer.com/guides/using-gmail), [Google: Sign in with app passwords](https://support.google.com/mail/answer/185833?hl=en).
  - **Outlook — real constraint found via research 2026-09-19, changes the original plan**: an "email + app password" flow, the initial ask, does not actually work for Outlook as of 2026. Personal Outlook.com/Hotmail accounts have already dropped basic-auth SMTP entirely — app passwords for those accounts stopped functioning and can't even be regenerated; OAuth2/Modern Auth is the only path. Microsoft 365 *business* accounts are the one case where app-password/basic-auth SMTP still works today, but it's on a published countdown: unchanged for now, **disabled by default for existing tenants at end of December 2026** (admin-reversible), unavailable at all for tenants created after that date. Sources: [Patriot Mail: Outlook App Passwords Are Gone for Personal Accounts](https://patriotmail.ai/blog/microsoft-modern-authentication-outlook-app-passwords), [Microsoft Tech Community: updated SMTP AUTH deprecation timeline](https://techcommunity.microsoft.com/blog/exchange/updated-exchange-online-smtp-auth-basic-authentication-deprecation-timeline/4489835), [SMTP2GO: the end of Microsoft's Basic Auth for SMTP AUTH](https://www.smtp2go.com/blog/the-end-of-microsofts-basic-authentication-for-smtp-auth/).
  - **Resolved 2026-09-19 — build Outlook OAuth2 now, not deferred as a later follow-up.** `nodemailer` supports OAuth2/XOAUTH2 SMTP (`smtp.office365.com:587`, `auth: {type: 'OAuth2', accessToken}`, scope `https://outlook.office.com/SMTP.Send`) via a token obtained through Microsoft's identity platform (e.g. `msal-node`). Source: [Nodemailer: OAuth2](https://nodemailer.com/smtp/oauth2).
  - **Explicit UX requirement from the user, the real design goal here — reserved for detailed design next session**: the end *user* of Sachivji must never see or configure anything Azure/cloud-related — the experience should feel like any standard mail client (type your email, the app figures out the server and handles sign-in), not a manual OAuth/Azure setup wizard. This is achievable but not free: the way Thunderbird/Apple Mail/Outlook desktop pull this off for a Microsoft account is that **the app itself** owns one pre-registered OAuth client (like an Azure/Entra app registration under this project's own control, analogous in kind to the code-signing accounts already tracked for #63/#65) and silently drives an interactive Microsoft sign-in popup behind the scenes — the user sees a login screen, not Azure. That one-time app-level registration is unavoidable for Outlook to work at all now that basic auth is gone/going away; what's fully avoidable is ever surfacing it to the end user. Exact flow mechanics (loopback-redirect vs. device-code, the specific Azure app registration and scopes, refresh-token storage) are explicitly deferred to a future session.
  - **Confirmation behavior**: `mutates: true`, a real confirmation dialog showing the recipients/subject/attachments before sending — matches this app's existing convention, and matters more here than most mutating actions, since an email is genuinely irreversible once sent, unlike most of this app's other actions which at least stay local.
