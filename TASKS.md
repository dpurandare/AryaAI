- [x] 105. Delegated turns no longer wedge a session on the next send — Implemented 2026-09-25 (0.2.1 hotfix)
  - **Found live, reported by the user, not assumed**: session "How many customers are there in northwind database?" failed on every send after its first delegation with `400 Invalid parameter: messages with role 'tool' must be a response to a preceeding message with 'tool_calls'` — the same error the #103 repair was meant to end. Replaying every real session through the actual `toOpenAIMessages` with a pairing checker (both directions) showed 4 of 6 sessions failing, 11 violations in all.
  - **Root cause**: a specialist runs in its own nested conversation (`dispatchDelegate`), but every message its `runLoop` yields is persisted to the same flat session table as it happens (`ipc/register.ts` `insertMessage` per orchestrator `message` event). Stored order is therefore: parent `tool_use delegate_to_x` → the specialist's own assistant/tool_result messages (`agentRole` set) → parent `tool_result` for the delegate. The parent's *live* conversation is correct (its delegate result follows its call; the nested run never enters it), so a turn works — only replay from SQLite is wrong: the delegate call looks unanswered and its real result looks like a `tool` message answering nothing. `repairDanglingToolUses` (#103) made it look half-fixed by adding a synthetic result after the call while leaving the real one orphaned.
  - **Fixed** in `src/main/context/prepare-context.ts`: `repairToolPairs`, three stages run first in `prepareConversation`. (1) `dropNestedDelegateMessages` removes the specialist's messages between a delegate call and its result — only when provably nested (every assistant message in the gap carries `agentRole`; every result in it answers a call made inside it; no real user message in between), since the parent never saw them and the delegate result already carries the specialist's final text. Handles nested-in-nested and parallel calls. (2) `synthesizeMissingResults` (the old #103 logic) for genuinely dangling calls. (3) `dropOrphanResults`, a final invariant: a `tool_result` must answer a `tool_use` in the assistant message right before it, else it is dropped — the backstop for any shape the first two didn't anticipate. Only affects what's sent; SQLite and the UI transcript are untouched.
  - **Verified**: 11 new tests (real-shape reproduction asserting the raw history is wire-invalid, then repaired; two-level nesting; parallel delegate + ordinary tool; sequential delegations; the untagged-fallback case for sessions saved before `agentRole` markers existed; turn-boundary safety; orphan drop; idempotence; no mutation), plus a reusable OpenAI-wire pairing checker in the test file. One pre-existing test fixture (a bare `tool_result` with no call) was itself the orphan shape and was corrected. 866/866 full suite, typecheck clean. Also run through the full `prepareConversation` for all 6 real sessions, including with a tiny context budget forcing the sliding window to drop turns: 0 violations in both, against 11 raw.
  - **Not covered / next**: the root cause — persisting nested messages interleaved in the parent's stream — is unchanged; this repairs at replay. A proper fix (tagging nested messages so the transcript and replay both know, or the handoff contract in `design-discussion.md` §5.1) belongs to the redesign. Not yet re-verified live in the running app (needs a restart).

- [x] 110. Track A1 — managed workspace runtime: `ensureWorkspace(root)`, Python venv created with the workspace, Settings > Runtime — Implemented 2026-09-26 (design-discussion.md 4.3 / section 10 Track A)
  - **Decision (Deepak, 2026-09-25; defaults approved 2026-09-26):** Python is a prerequisite and the venv is created with the workspace and its folders, not improvised by an agent. New `src/main/runtime/workspace-runtime.ts` (+ shared `src/shared/runtime.ts`): idempotent `ensureWorkspace(root)` creates `code/ documents/ resources/`, then the venv; a state machine `missing-python | creating | ready | failed | disabled` (+ a `packages` sub-state) with change notifications. Called at startup and from `WorkspaceSetRoot` (a venv embeds absolute paths, so each root needs its own).
  - **Detection:** `python3`/`python` (`py -3` first on Windows) probed with a 15s timeout; the probe imports `venv` **and** `ensurepip` (Debian ships them separately) and requires Python >= 3.10, with a specific reason for each failure.
  - **Base packages are pinned and chosen to fit Python 3.10** — checked against PyPI `requires_python`, not assumed: the newest numpy (2.5.3) needs 3.12 and matplotlib 3.11.2 needs 3.11, which would have silently raised the floor. Pins: matplotlib 3.10.9, numpy 2.2.6, pillow 12.3.0, python-docx 1.2.0, openpyxl 3.1.5. Always `<venv python> -m pip`. Install is background, non-fatal, and retried by the next ensure via a `venv/.sachiv-runtime.json` marker (so "we made this and packages never finished" is distinguishable from "the user's own venv").
  - **Never destroys user content:** an existing working venv is adopted untouched (packages reported as `adopted`); a broken one, or a non-venv `venv/` folder, is reported and left alone until the user chooses Repair (which deletes it, behind a confirm); a failed creation removes only the partial venv that same call just made. A 600 MB free-space check runs first.
  - **Surfaces:** IPC `runtime:get-state / ensure / repair / set-enabled` + push `runtime:state-changed`; Settings > Runtime shows state, Retry, Repair… (confirm), Turn Python on/off (`pythonRuntimeDisabled` setting → `disabled`). The `shell_execute` no-venv hint now points at Settings > Runtime instead of telling the model to build a venv itself.
  - **Verified:** 21 new tests (fake filesystem + scripted runner, both platforms, every branch above; the stale-root test was mutation-checked — fails with the guard removed); full suite 905/905, `typecheck` clean (node + web). **Real end-to-end run** against the machine's Python 3.12.3 in a scratch workspace with a space in its path: folders + venv + all five packages installed in 8s, all five import, a second launch reported `ready/installed` without redoing anything.

Whole-turn failures no longer silently resent as unanswered "real" context, forever — found live tracing a real Groq session (4 identical retries of the same question): a thrown provider error left literally nothing persisted (the user's message had already been inserted before `orchestrator.run()` even started), a Stop click before any content produced also left nothing, and an empty/no-output round only ever left a UI-only `warning` block — every provider adapter strips `warning` from the wire format entirely, so even that was invisible to the model.
