Unlike `page-creator`, `email` **is** included in `AGENT_ROLES` (user-selectable via the Ctrl+Tab picker, and a valid classify-and-plan step target) — "send an email about X" is a perfectly normal standalone request, unlike a one-slide brief.
  - **Confirmation behavior**: `mutates: true`, a real confirmation dialog showing the recipients/subject/attachments before sending — matches this app's existing convention, and matters more here than most mutating actions, since an email is genuinely irreversible once sent, unlike most of this app's other actions which at least stay local. **Implemented as designed** (`send_email`'s `describe()`).

  ### Phase 2 (documented now, build later): Outlook / Microsoft 365 / Hotmail
  **Real constraint that shaped this whole design, confirmed via research 2026-09-19/21, sources throughout**: plain email+password (with or without 2FA) cannot work here at all — this isn't an app-password-specific gap, Basic Authentication itself (the underlying SMTP username/password login mechanism) is being retired industry-wide for Microsoft's mail services. Personal Outlook.com/Hotmail accounts have *already* dropped it entirely (app passwords for those accounts stopped working and can't be regenerated). For Microsoft 365 business accounts, secondary sources disagree on the exact date (one says Basic Auth for SMTP AUTH is disabled by default for existing tenants end of December 2026, admin-reversible until then; another says Microsoft already permanently disabled it March 1, 2026 with full retirement, no exceptions, by April 30, 2026) — don't trust either blog for the precise date; check [Microsoft Learn's own deprecation page](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/deprecation-of-basic-authentication-exchange-online) directly when this is actually built. The actionable fact is date-independent: OAuth2 is mandatory, now or very soon, no exceptions.
  - **Why the user's own mail client never showed an Azure/Entra screen — explains the whole design below, not a loophole to route around**: Microsoft's own first-party apps (Outlook for Mac/iOS) get to accept a real password directly because the app itself already carries Microsoft's own trusted identity. Non-Microsoft apps (Apple Mail, Thunderbird) do a *real* OAuth 2.0 flow behind an embedded, native-feeling sign-in view — each has its own pre-registered app identity (Apple's, Mozilla's) — that's what makes the OAuth screen invisible-feeling. Sachivji needs the exact same shape: its own pre-registered app identity, so the *end user* only ever sees a plain Microsoft sign-in popup, never Azure configuration. Sources: [Apple Community: Apple Mail MFA](https://discussions.apple.com/thread/254336647), [Microsoft Support: Modern Auth for non-Microsoft email apps](https://support.microsoft.com/en-us/office/modern-authentication-methods-now-needed-to-continue-syncing-outlook-email-in-non-microsoft-email-apps-c5d65390-9676-4763-b41f-d7986499a90d), [Bugzilla: Thunderbird's own O365 2FA support ticket](https://bugzilla.mozilla.org/show_bug.cgi?id=1528136).
  - **Resolved — use Microsoft Graph's `sendMail` API, not SMTP OAuth2.** The original plan (nodemailer's XOAUTH2 SMTP transport against `smtp.office365.com`) works, but Graph is Microsoft's actual current recommendation: it isn't exposed to the SMTP-AUTH retirement at all (a completely different API surface), supports personal Outlook.com/Hotmail accounts via the same delegated `Mail.Send` scope as work/school accounts, and automatically writes to Sent Items (SMTP doesn't). `nodemailer` has no first-class Graph transport, so the Outlook send path is a plain authenticated `POST https://graph.microsoft.com/v1.0/me/sendMail` call, not routed through `nodemailer` at all — Gmail keeps using `nodemailer`, Outlook uses a direct Graph call; the isolated `email` role's tool implementation branches by the connection's provider, both exposed as the same `send_email`-shaped action to the model. Sources: [Dartmouth: SMTP OAuth2 vs Graph FAQ](https://services.dartmouth.edu/TDClient/1806/Portal/KB/ArticleDet?ID=168187), [Unipile: Microsoft Graph Email integration guide](https://www.unipile.com/microsoft-graph-api-email-integration-guide/).
  - **App registration — Sachivji needs exactly one, shared by every user of the app (not one per user, not something an end user ever creates).** Step-by-step, to actually follow when this phase is picked up (verify each step against the live Entra admin center UI first, since portal UIs shift):
    1. Sign in to the [Microsoft Entra admin center](https://entra.microsoft.com) with a Microsoft account under this project's control (a personal Microsoft account is sufficient for creating an app registration — no paid Azure subscription required for this).
    2. **App registrations → New registration.**
    3. Name: `Sachivji` (or similar — user-visible only on the consent screen, e.g. "Sachivji wants to: Send mail as you").
    4. **Supported account types: "Accounts in any organizational directory (Any Microsoft Entra ID tenant – Multitenant) and personal Microsoft accounts (e.g. Skype, Xbox)."** This is the one that makes both personal Outlook.com/Hotmail and any organization's Microsoft 365 work — picking a narrower option (single-tenant, or org-only) would silently break one of the two account types this item targets.
    5. **Redirect URI**: platform type **"Mobile and desktop applications,"** value `http://localhost` (loopback — the modern MSAL pattern for a native app using the system browser; libraries like `msal-node` bind an actual free port at runtime and match against the registered `http://localhost` base). Do not use the legacy `https://login.microsoftonline.com/common/oauth2/nativeclient` redirect URI some older docs show — that's an ADAL-era pattern, not the current MSAL/loopback approach this design uses.
    6. After creation, copy the **Application (client) ID** from the Overview page — this is the one value the app's code needs; **no client secret is created or used**, since a public/native client authenticates via PKCE, not a secret (a desktop app can't keep a secret safe anyway).
    7. **Authentication** blade → under "Advanced settings," confirm **"Allow public client flows" = Yes**.
    8. **API permissions** → Add a permission → Microsoft Graph → **Delegated permissions** → add `Mail.Send`, `offline_access` (needed for a refresh token — without it, the user would have to re-sign-in every ~60-90 minutes), `openid`, `profile`, `email`. These are all user-consentable delegated scopes; **no admin consent grant is needed for personal accounts**, and for most Microsoft 365 tenants a regular user can consent to these specific low-risk scopes themselves the first time they sign in — flag honestly in the UI that a minority of locked-down organizations may require their own IT admin to approve it once, since that's outside Sachivji's control.
  - **Token flow at runtime**: `msal-node`'s `PublicClientApplication` with `acquireTokenInteractive` (handles the loopback listener itself in current versions) using the client ID from step 6 and authority `https://login.microsoftonline.com/common` (the multi-tenant + personal endpoint matching step 4). Store the resulting refresh token in the keychain (or `.env` per #75) keyed `email:outlook:<accountId>`, dual-written per #75's resolved design; access tokens are short-lived and re-derived on demand via `acquireTokenSilent`, never persisted. A silent-refresh failure (`invalid_grant`, revoked consent, tenant policy change, or the token simply going stale from disuse) must surface as "please sign in again," not a silent failure — re-run the same interactive flow.
  - **End-user-facing flow, addressing the "well-orchestrated flow, not just documentation" requirement directly**: Settings → Email → "Add email account" shows two provider buttons, Gmail and Outlook/Microsoft, each with a one-line explainer so the visibly different flows don't look like an inconsistent or broken UI:
    - *Gmail*: "Sign in with your email and an app password" → the form described in Phase 1 above.
    - *Outlook/Microsoft 365*: "Sign in with Microsoft" (single button, no form fields at all) → opens the user's real default system browser (never an embedded webview inside Sachivji — a native app popping up its own login-look-alike window is exactly the shape of a phishing attack, and Microsoft's own guidance for native apps is to use the system browser) to Microsoft's actual `login.microsoftonline.com` page → user signs in and completes their own MFA there, entirely on Microsoft's real domain → browser redirects to `http://localhost:<port>/callback`, where Sachivji's already-listening local server catches the code, exchanges it, and closes the browser tab automatically → Settings shows "Connected: `<email>`" for that account.
    - Both paths land in the same place afterward: Settings lists every configured send-from account (masked where relevant), each independently removable/re-connectable, mirroring the pattern already used for DB/API/MCP connections.
  - **Confirmed alignment with the user's explicit position** ("I am not in favor of the app password right now" for Outlook): this design has zero app-password path for Outlook — Gmail keeps app password (the one place it's still genuinely durable), Outlook is 100% the OAuth2/Graph flow above.
