# 9. The user interface

The UI is a **Svelte 5** app (runes mode) in `src/renderer`, built by Vite through electron-vite. It talks to the main process only through `window.sachiv` (see [Architecture](03-architecture.md)).

## Layout of the code

```
src/renderer/
  index.html        the app page (its own Content-Security-Policy)
  print.html        the hidden page used for PDF export (its own CSP)
  src/
    main.ts         entry for the app page: theme init, mounts App.svelte
    print-main.ts   entry for the print page
    App.svelte      the single top-level component: owns nearly all state (about 1,100 lines)
    theme.css       the colour palette (CSS variables), shared by both pages
    lib/            plain TypeScript helpers and the components folder
      components/   ChatView, SessionList, SettingsPanel, ToolConfirmDialog, ModelPicker,
                    ContextMeter, MarkdownText, FirstRunSetup, SplashScreen, AccountMenu, PrintView
      markdown.ts, theme.ts, context-meter.ts, handoff-tag.ts, tool-input-display.ts,
      mermaid-render.ts, search-history-result.ts   (each with a .test.ts)
```

## State: App.svelte and per-session runtimes

`App.svelte` is the state owner; the components receive data and callbacks as props. The key idea is **per-session runtime state**:

- `sessions` and `activeId` say which chats exist and which is shown.
- `runtimes` is a record keyed by session id. Each `SessionRuntime` holds everything that changes while that session's turn runs: its `messages` (as `DisplayMessage[]`), `sending`, `currentStreamId`, `pendingConfirm`, `pendingLimit`, token usage and context size.
- Switching `activeId` only changes which runtime is **shown**; it never touches the others, and a session's own stream listener (set up in `sendMessage`) closes over its own runtime object. This is what lets several chats generate at once, and what prevented a past bug where switching sessions mid-stream pointed a stale array index at another session's messages. A background session that needs a confirmation waits quietly (the session list shows an activity dot); the dialog only appears when you look at that session.

`DisplayMessage` holds ordered **segments** (`text`, `tool`, `thinking`, `warning`, `user_note`), each optionally tagged with the `agentRole` that produced it, so interleaving (text, a tool call, more text) and attribution render correctly. A tool segment carries its call, result and any `show_media` image. `plan` and `statusText` are live-only and never stored.

Stored messages (`ContentBlock[]` with `tool_result` messages as continuations) are folded into segments when a session loads. Live events (`StreamEvent`s) are applied to the same structure as they arrive (`sendMessage` in `App.svelte` has the full mapping), so a reloaded session looks like a live one.

## Svelte 5 gotchas the code has already hit

Both look correct and fail silently:

- **Stale object after `push`.** `runtime.messages.push(obj)` deep-proxies `obj`; later mutations through the *original* reference never reach the reactive graph (a pending spinner that never stopped). Always mutate through the proxied element, for example `runtime.messages[index]`, looked up again when needed.
- **`$state(Set)` and `$state(Map)` are not deep-reactive.** Replace the whole collection (or use a plain object or array) instead of mutating it in place.

## Rendering model output safely (`lib/markdown.ts`)

Model and tool text is untrusted. The pipeline is: `marked` to HTML, **DOMPurify** with an explicit tag and attribute allowlist (no `<img>`, no event handlers), KaTeX for math and Mermaid for diagrams spliced back in **after** sanitising using their own trusted output (so the allowlist is never widened for their markup). Local images appear only through `image` blocks (data URIs from `show_media`), never as Markdown images in text.

The renderer's CSP (`index.html`: `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:`) enforces this a second time. `print.html` has its **own** CSP, and it must allow whatever the print page renders: it once lacked `img-src data:` and every picture in a PDF came out broken.

`markdown.ts` also holds a renderer-side copy of the handoff tag parser (`parseHandoffTag` semantics) so a pinned role's `[handoff: …]` line is not shown; main and renderer are separate processes, so it cannot import the main one. Keep the two in step.

## Theme

`theme.css` defines CSS variables (`--bg`, `--panel`, `--text`, `--accent`, and so on) for dark by default and `:root[data-theme='light']` for light, tuned separately (not an inversion). `lib/theme.ts` reads the stored `themeMode` (`light`, `dark`, `system`) before the app mounts, sets `data-theme` on `<html>`, and tracks the OS setting live when `system` is chosen. Use the variables, never hard-coded colours.

## Shortcuts and window behaviour

- **In the renderer:** `Cmd/Ctrl+O` cycles the tool-output display (App.svelte), `Enter` / `Shift+Enter` and `Ctrl+Tab` / `Ctrl+Shift+Tab` in the composer (ChatView). `Ctrl+Tab` stays Ctrl on macOS because Cmd+Tab belongs to the system.
- **In the main process:** zoom (`Cmd/Ctrl +`, `-`, `0`, `window/zoom.ts`), window bounds persistence (`window/bounds.ts`), the spell-check context menu (`window/context-menu.ts`). The macOS title bar is `hiddenInset` with a custom traffic-light position, and the CSS pads for it (`App.svelte`).

## The print page

`PrintView.svelte` loads the session through the same `window.sachiv` calls, renders it with the same Markdown component, and calls `notifyPrintReady()` once the DOM, fonts and images are ready. Main (`sessions/export.ts`) waits for that signal (with a timeout), then calls `printToPDF`. It honours the same tool-output display mode as the live view; images are always shown.

## Verifying UI changes

Type checks, the build and unit tests can all pass while a panel is broken. Check a UI change in a **running** app: build, launch a throwaway profile, and drive it over the Chrome DevTools Protocol (`--remote-debugging-port`). The documentation screenshot scripts (`scripts/docs-screenshots/`) are a working example: they launch a packaged build on a throwaway profile with a fake home folder, seed the database, replace `chat:send` in the main process (through `--inspect`) so a turn can be driven by hand, and capture only the window contents. Use a throwaway copy of any database you inspect, and delete it afterwards.

## Adding UI

- A new Settings section goes in `SettingsPanel.svelte` (sections are in a fixed order; keep the order in the User Guide's Settings reference in step).
- New data from the main process needs an IPC channel (see the [extension checklists](appendix-extension-checklists.md)).
- Text shown to the user should be plain and specific; error text should say what to do next.
